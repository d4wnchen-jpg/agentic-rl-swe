# 关键发现与实验记录（2026-11-03）

> 项目：code agent 上的可执行验证 pivot 信用标签（VPD）。
> 目的：用两周验证「pivot 机制在 code 场景成立到什么程度」，决定论文选题（11-10 go/no-go）。
> 详细方法/报告：`smoke_test/L1_ORACLE_REPORT.md`（仓库 `docs/L1_ORACLE_REPORT.md`）
> 数据：`results/{g1c,g2a,r3a}/`；代码：仓库 `oracle/`。

## 一、核心结论（TL;DR）

1. **pivot 机制成立，但产出率由「实例的失败模式」决定**：
   - 改坏/可恢复型轨迹（flask-5063）→ 产出 harmful + (mistake, recovery) 配对（7/10 轨迹有配对）；
   - 只修一半 / 修好型轨迹（flask-4045、requests-3362）→ 产出 beneficial 标签（5/5、5/5）。
2. **跨 3 个 repo（flask×2、requests×1）可复现**：20 条轨迹中 **12/20 = 60%** 有 cf-verified 标签；8 个 recovery 配对（原始因果 7/8）。
3. **重放保真度通过**：5/5 轨迹重放后的代码与 agent 提交 patch 完全一致（唯一差异是 agent 自产的 `patch.txt`）。
4. **教师对照（修正语义后）**：
   - 有可归因错误时，教师 exact **4/5 = 80%**（它能定位）；
   - **无可归因错误时，教师仍指认 pivot 13/15 = 87%**；仅 2/20 次回答「没有关键步」。
   → 教师的增量是“定位”，我们的增量是 **signed（有害/有益）+ “无 mistake”判定**。
5. **反事实 > 补丁回滚**：长轨迹反复改同一文件时，`git apply -R` 必然冲突；skip-turn 重放（以及文件级回滚兜底）才可靠。
6. **标签语义是“对失败测试数的影响”**，不是“策略正确性”：beneficial 的编辑仍可能是错方向，只是修好了一个测试。

## 四、方法学要点（踩坑沉淀）

1. **diff hunk ≠ 语义编辑**：gold patch 的一个功能改动会被切成互相依赖的 hunk，单独回滚会 Type/语法错误；粒度应按 **agent 的一次 edit/命令**。
2. **nodeid 是 shell 不可信输入**：含 `&`/`#` 的 parametrized ID 会被 bash 解析坏；必须 `shlex.quote`。
3. **评测必须复刻官方语义**：`git checkout base -- <test files>` → apply test_patch → `pytest -rA <整个测试文件>`；按 nodeid 子集跑会因顺序得到不同结果。
4. **实例准入筛查**：baseline `n_fail == len(F2P)` 且 P2P 全过；requests-2674 就是反例（12 个 F2P 里 11 个在 base 通过 → 标签噪声，弃用）。
5. **反事实有效性**：skip 某轮会让后续命令失败（本属反事实的一部分）；判据应为「相对原轨迹是否多出失败」，且需文件级回滚兜底。
6. **双向标签**：`beneficial` 必须单独验证（跳过它 → 终态变差），否则 omission 型轨迹产出率为 0。
7. **提交产物要忽略**：`patch.txt` 等 agent 自产文件不属于代码改动。
8. **Codespace 操作**：Docker 镜像不持久；磁盘 32G 一次只放一个镜像；`tail -f` 不会自动退出（用 Ctrl+C）。
