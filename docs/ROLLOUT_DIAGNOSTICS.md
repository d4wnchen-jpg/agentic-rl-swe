# Rollout 管线诊断报告

## 单卡 Agentic RL 的六类信号故障与修复

**版本** v1.0 · 2026-11-02
**项目** agentic-rl-swe（MIT）· Qwen3.5-9B + LoRA + vLLM + GRPO · SWE-smith
**环境** 1× RTX PRO 6000 96GB，无 Docker 容器，AutoDL

---

## 0. 摘要

在一张 96GB 单卡、无 Docker 的容器里跑通 agentic RL 全流程（沙箱 → 多轮 rollout → 判分 → GRPO → 权重回灌），20 步训练、640 条 rollout。过程中定位到 **6 类故障**，其中：

| 级别 | 故障 | 一句话后果 |
|---|---|---|
| **P0** | 训练/推理 chat template 渲染不一致 | 训练后 96% 的 rollout 复读 |
| **P0** | 判分材料对模型可见 + 观测截断 | 完成信号丢失，99% 的 rollout 轮数耗尽 |
| **P1** | 评测集构成本身是混杂变量 | 真实 +80% 的相对提升被稀释成总分 +2 道题 |
| **P1** | 零方差组占 36% | 三分之一的算力不产生梯度 |
| **P2** | 评测噪声 ±6pp | 翻转量是净变化的 12 倍，单次评测无法下结论 |
| **P2** | 训练后行为漂移 | 不是"变懒"，是对坏环境的适应 |

**核心结论：agentic RL 的失效模式首先出现在「信号链」上——渲染 → 观测 → 判分 → 统计——而不是在优化器上。** 六类故障里有 4 类的修复成本为零或接近零（不需要 GPU），1 类需要重训，1 类需要扩训练量。

**证据边界：** 本文所有数据来自 20 步 / 640 条 rollout 的单次实验，评测噪声 ±6pp。低于 6pp 的差异一律不当作结论，只当作方向性观察。

## 1. 系统背景与约束

### 1.1 回路

```
① 造沙箱      checkout 缺陷分支 → 打补丁 → 移除 .git 等防作弊
② Rollout     vLLM + LoRA，最多 40 轮；模型动作 → 沙箱执行 → 观察拼回
              记录 prompt_ids / response_ids / per-token logprob，不裁剪历史
③ 判分        任务结束时一次：恢复被删的 F2P 测试 → pytest
              reward = 1.0 iff F2P 全过 且 P2P 全过
④ 优势        rollout 级组内归一化 A_i = (r_i - mean) / (std + 1e-4)
⑤ 拼训练行    LCP 前缀链对齐，40 轮拼成一条约 25k token 的序列
⑥ 更新        2 次 mini-batch，per-rollout mean loss
⑦ 回灌        存 LoRA → 换 LoRARequest → 回 ②
```

配置：`n_rollouts=8`、`n_prompts=4`、`steps=20`、`max_turns=40`、`max_row_tokens=32768`、
`lr=1e-4`、`clip=0.2/0.28`、评测温度 0.7。每步约 27 分钟（rollout 850–2300s，训练 315–442s），
峰值显存 88.4/96 GB。

### 1.2 关键约束

| 约束 | 值 | 影响 |
|---|---|---|
| GPU | 1× 96GB，vLLM 与训练共用 | 不能"多卡多 rollout"，故障代价被放大 |
| 容器 | 无法用 Docker | 沙箱靠目录 + 环境变量隔离，判分环境按仓库分 conda env |
| 任务量 | 187 题（参照实现 6,000 题） | 统计功效不足，必须分层 |
| 训练量 | 640 条 rollout（参照实现 128,000 条） | 只够验证工程，不够验证能力 |
| 评测集 | 113–115 题，74% 是基座做不动的题 | 总分被严重稀释 |

### 1.3 为什么故障集中在信号链

这条管线有 7 个环节，每个环节都包含一次**转换或截断**：模板渲染（格式转换）、观察拼接（截断到 `obs_cap`）、判分（还原 F2P 测试）、优势归一化（组内统计）、评测（抽样与温度）。每一处转换都可能改变"模型实际看到的东西"，而其中任何一处不一致，最终都会以"训练没效果""模型变笨"的形式表现出来。

**排查 agentic RL 的故障时，先怀疑信号链，后怀疑优化器。**

## 2. 诊断方法

### 2.1 三层观测

| 层 | 观测什么 | 工具/产物 |
|---|---|---|
| **token 级** | prompt 渲染结果、mask、per-token logprob、前缀链是否连续 | LCP 对齐测试、模板单测 |
| **轨迹级** | 每轮动作、观察是否被截断、轮数、终止原因 | 轨迹审计（六类判定） |
| **任务级** | reward、分层通过率、零方差比例、行为代理指标 | 评测脚本 + 分层报表 |

### 2.2 四个排查手段

1. **与参照实现逐字 diff**：模板、提示词、`obs_cap`、超参。本项目声称的四处"对齐"，三处没对齐。
2. **单变量重放**：同一份权重只换一个配置。例：step020 权重分别在 `enable_thinking=False` 与不传参下评测，各 59 题。
3. **行为代理指标**：编辑率、pytest 调用率、主动提交率、轮数耗尽率。能力没变时，行为先变。
4. **分层统计 + 多轮平均**：mixed / allpass / allfail 分开报，评测 k>1 次取平均。

### 2.3 一条铁律

> **从症状反推根因，不要选最省事的解释。**

本项目在这上面错过一次：

```
症状：轮数耗尽 99%、主动提交 1/113
  最省事的解释 → "训练量不够" → 加 24× 训练量（≈140 小时）→ 什么都不会变
  实际根因     → prompt 尾部有可复制的块 + 输出被截断，模型拿不到"我完成了"的信号
```

正确做法：先把"症状能推出哪几种原因"列全，再逐条用数据排除。

## 3. 故障详单

### P0-1　训练/推理 chat template 渲染不一致

**现象**
step020 权重评测时，108/113（96%）的 rollout 出现复读，复读内容固定为 `<think>\n\n</think>\n\n`，累计 153,796 次，单条最长 77,824 字符（约 25k token）。

**证据**
- 该片段在训练数据里 `mask=0`——**模型从未被训练生成它**；
- 每条 prompt 里恰好只有 1 个该片段，排除"每轮重复强化"；
- 生成点插入、历史渲染不插入 → 相邻两轮**不构成 token 前缀链**；
- 用修好的模板重跑 59 题：复读率 **90.3% → 0%**。

**根因**
Qwen3.5 原生模板在生成点无条件插入完整空思考块，而历史渲染走另一套逻辑（还额外剥离 assistant 内容里的 think 块）。参照实现的自定义模板让"生成提示符 = 内容为空的历史渲染"，两处同一个条件、同一个字符串。

**影响**
- 通过率：复读组 24.5% vs 基座 23.9% —— **无影响**；
- 上下文：平均浪费 23,474 字符（上限 200,000 的 12%）、约 1 轮（共 40 轮）；
- **这是"浪费"，不是"损害"**，但它是格式不匹配的警报。

**修复**
使用自定义模板（`tools/tpl_chat.jinja`），生成点与历史渲染共用一套逻辑。
⚠️ **换模板等于换格式，必须重训**：只换推理配置不重训，同题通过率 25.4% → 15.3%（`SE_diff ≈ 7.4pp`，不显著，但方向危险）。

**残留风险**
现有权重只能继续用 `enable_thinking=False` 评测（训推一致）；修复的价值要靠新配置重训才能兑现。

---

### P0-2　判分材料对模型可见 + 观测截断

**现象**
测试文件对模型开放时，模型会直接去跑测试套件。pytest 输出几万字符，被 `obs_cap`（8000）截断到只剩最后约 66 个测试——**拿不到"我完成了"的信号**。

**证据**
| | 基座 | step020 |
|---|---|---|
| 轮数耗尽 | 112/113（99%） | 85/113（75%） |
| 主动提交 | 1 | 19 |
| 跑过的测试覆盖多少 F2P | 34.8% | 30.2% |

最终通过的 27 道题里，**只有 7 道（26%）模型自己看到过"全绿"**。

**根因**
两个设计叠加：① 判分测试对模型可见 → 模型依赖测试输出判断成败（reward hacking 风险）；② 观察预算（`obs_cap`）低于真实输出长度 → 关键信号被截掉。

**影响**
模型被训练成"早交、少验证"（见 P2-6）。这不是能力问题，是**观测接口问题**。

**修复（分两步）**
1. ✅ 已做：题面引导模型"写最小复现脚本 → 改 → 重跑确认"，补回工作流；
2. ⏳ 待做：沙箱里移除 F2P 测试文件（判分前恢复），让模型必须自己构造验证。

**残留风险**
移除测试文件后，模型可能转向"自证正确"（自己写的测试遮盖真实失败），需要同时引导"最小复现 + 保留原始失败输出"。

---

### P1-3　评测集构成本身是混杂变量

**现象**
总分 23.9% → 25.7%（+2 道题），看起来"RL 无效"。但按难度分层：

| 层 | 题数 | 基线 | step020 | 变化 |
|---|---|---|---|---|
| **mixed（有学习信号）** | 17 | 5/17 | **9/17** | **+4（相对 +80%）** |
| allpass | 12 | 10/12 | 10/12 | 0 |
| allfail | 84 | 12/84 | 10/84 | −2 |
| **合计** | 113 | 23.9% | 25.7% | +2 |

**根因**
评测集 74% 是基座做不动的题（allfail）。它们对训练不敏感，却在总分里占大头，把 mixed 层 80% 的相对提升稀释成总计 +2 道题。

**影响**
任何不分层的实验都测不出效果——这是**所有后续实验的前提**。

**修复**
免费：评测集分层报告（mixed / allpass / allfail）。

---

### P1-4　零方差组占 36%

**现象**
20 步 × 4 题 = 80 组，其中 29 组（36%）8 条 rollout 全对或全错，优势恒为 0，不产生梯度。有效信号只有 64%。

**影响**
- "检测 12pp 需要 15× 训练量"要按有效信号修正为 **×24**（≈140 小时单卡）；
- 训练曲线单步 SE ≈ 8.5pp（只有 32 个样本），波动主要来自题目难度，不是学习效果。

**修复**
题目池动态化：把已稳定做对的题移出（DAPO 的 Dynamic Sampling），全错的题按比例补。成本：小，但需要题目池。

---

### P2-5　评测噪声 ±6pp

**现象**
同一配置两次评测，方向相反：

| 评测 | 基座 | step020 | 变化 |
|---|---|---|---|
| 第一次 | 30.1% | 27.4% | −2.7 pp |
| 第二次 | 23.9% | 25.7% | +1.8 pp |

基座自身两次相差 **6.2pp**。逐题看：fail→pass 13 道、pass→fail 11 道，净变化 +2，但**总翻转 24——翻转量是净变化的 12 倍**。

**根因**
113 题的评测集 + 温度 0.7 + 单次采样，统计功效不足。要检测 12pp 提升（80% 功效，α=0.05）需要 ≥147 道题。

**修复**
扩题到约 150 道；评测取 k>1 次平均；固定评测脚本与温度；结论只认分层 + 多轮平均后的方向。

---

### P2-6　训练后行为漂移：不是变懒，是适应

**现象**
| | 基座 | step020 |
|---|---|---|
| 从未编辑过任何文件 | 36% | **68%** |
| 从未跑过 pytest | 26% | **55%** |
| 平均编辑次数 | 1.9 / 条 | 0.5 / 条 |

而 step020 内部：**成功组跑 pytest 的比例 86%，失败组只有 44%**——"少验证"和更低成功率直接相关。

在两次都失败的 73 道题上，至少编辑过一次代码的比例：64% → 36%。

**根因**
这是对坏环境的适应，不是能力退化：反正跑测试看不到结果（P0-2），不如少跑、早交。**行为是先被环境塑造的。**

**修复**
先修 P0-1 / P0-2，再重训。修完环境后重跑同样的行为指标，确认编辑率恢复。

## 4. 影响矩阵：这些故障会让你得出什么错误结论

| 故障 | 直接症状 | 若误判会得出的结论 | 实际代价 |
|---|---|---|---|
| P0-1 渲染不一致 | 96% 复读 | "模型能力退化 / 训练崩坏" | 换模型、加训练量，全部无效 |
| P0-2 判分可见 + 截断 | 99% 轮数耗尽 | "模型笨、不会用工具" | 训出"少验证早交"的行为 |
| P1-3 评测集混杂 | 总分纹丝不动 | "RL 无效" | 真实 +80% 被 74% 无效题稀释 |
| P1-4 零方差 | 曲线噪声大 | "训练量不够" | 36% 样本无梯度，预算浪费 |
| P2-5 评测噪声 | 两次方向相反 | "有效 / 无效"随机 | 结论不可信 |
| P2-6 行为漂移 | 编辑率下降 | "RL 让模型变懒" | 环境适应，不是能力退化 |

**这张表的用法：任何一次"训练没效果"的判断，先对着它排除一遍，再决定要不要加算力。**

## 5. 修复优先级与算力账

| 优先级 | 动作 | 依据 | 成本 | 依赖 |
|---|---|---|---|---|
| 1 | 修 P0-2：移除 F2P 测试文件 + 保留工作流 | 坑 2 | 小（无 GPU） | 无 |
| 2 | 评测集分层报告 | 坑 3 | 免费 | 无 |
| 3 | 评测扩到约 150 道 | 坑 5 | 免费（题量） | 题目 |
| 4 | 动态题目池（Dynamic Sampling） | 坑 4 | 小 | 题目池 |
| 5 | 自定义模板 + 训推一致**重训** | 坑 1 | ~9h | 1 完成之后 |
| 6 | 评测 k>1 次平均 | 坑 5 | 时间 ×k | 无 |
| 7 | SFT 冷启动（用已有成功轨迹） | 基线 27 道成功 | 数据 + 短训练 | 5 之后 |
| 8 | 训练量提到 ≥10,000 rollout | 检测 12pp 需 ×24 | ~140h | 1–5 之后 |

**关键依赖：先修 1 + 2，再重训。** 否则重训出来的行为仍然建立在"看不到完成信号"的环境上，等于白跑 9 小时。

**算力账（单卡 96GB）**

| 项 | 值 |
|---|---|
| 每步耗时 | ~27 分钟（20 步 ≈ 9 小时） |
| 检测 12pp 的最低门槛 | ≥147 评测题、≥10,000 rollout、~140 小时（≈15×） |
| 复现参照实现（128,000 rollout） | 约 1,800 单卡小时 ≈ 75 天；参照实现用 4×B200 |

**结论：单卡适合"跑通流程 + 验证工程方案"，不适合"产出可信的性能提升"。**

## 6. 上线前检查清单（可移植到任何 agentic RL 管线）

1. **训推一致**：训练与推理的 prompt 渲染是否逐 token 一致？用前缀链测试验证，不靠肉眼。
2. **生成点 = 历史渲染**：特殊 token（think 块、工具标记）在生成点和历史里是否同一套逻辑？
3. **完成信号**：模型能否从观测里拿到"我做完了"的客观信号？谁给它的？
4. **判分可见性**：判分材料对模型是否可见？可见就是 reward hacking 面。
5. **截断策略**：`obs_cap` 是多少？截断丢掉的是尾部信号还是无关噪声？
6. **评测分层**：mixed / allpass / allfail 分开报了吗？不分层 = 实验白做。
7. **零方差比例**：全对/全错组占比多少？超过 20% 就要做动态采样。
8. **噪声估计**：同一配置重跑两次，差多少？k>1 平均了吗？
9. **行为指标**：编辑率、工具调用率、提交时机——能力没变时行为会先变，它们是早期警报。
10. **恢复与幂等**（本项目空白，下一版补）：中断后能否续跑？判分/回灌是否幂等？

## 7. 结论与下一步

**结论**

- 单卡跑通了完整回路，工程侧是成立的；
- held-out 总分 +2 落在噪声内，**这个预算下测不出能力变化**；
- mixed 层 5/17 → 9/17（相对 +80%）是唯一方向明确的正信号，但样本只有 17 道；
- 六类故障中，4 类零算力可修，且**必须排在重训之前**。

**下一步**

1. 修 P0-2（移除 F2P 测试）→ 分层报告 → 扩评测到 150 题；
2. 用自定义模板重训一次（训推一致），重跑行为指标；
3. 题目池动态化，把 36% 的零方差组压下去；
4. 训练量提到 ≥10,000 rollout，再谈"可信的提升"；
5. 补断点恢复与幂等（本报告未覆盖的部分）。

**一句话**：这份报告的价值不在"训练效果如何"，而在**"在得出任何训练结论之前，先把信号链修对"**——顺序错了，算力全是沉没成本。

## 附录 C　术语

| 术语 | 含义 |
|---|---|
